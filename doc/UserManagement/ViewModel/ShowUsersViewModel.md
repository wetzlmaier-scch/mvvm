# `UserManagement/ViewModel/ShowUsersViewModel.cs`

### Purpose

`ShowUsersViewModel` is the view model behind the user-list part of the user-management feature. It exposes the collection of users the UI displays, fetches that collection from the business layer when the view loads, and stays in sync with other view models by listening for `UserChangedMessage` broadcasts. Without it, the view that lists users would have no data source and no way to react to users being added elsewhere in the app.

### Role in the Codebase

This class is one of two sibling view models under `UserManagement/ViewModel` (`AddUserViewModel` handles creating users; this one displays them). It is `partial` — the other half is generated by the CommunityToolkit.Mvvm source generator, which turns the `[RelayCommand]`-annotated `OnLoadedAsync` into the `LoadedCommand` property declared on the interface.

It is consumed through the MEF composition root, not by direct construction:

- `[Export(typeof(IShowUsersViewModel))]` makes it available under its interface.
- `UserViewModel` (the parent, in `UserManagement/ViewModel/UserViewModel.cs`) has an `[Import] IShowUsersViewModel ShowUsersViewModel` property, so the container wires this class into the parent view model, which in turn is exported as `IMainViewModel`.

The `[Export]` attribute means `UserViewModel` is created by the MEF container, so the `Mvvm.ViewModelBase` design-mode support (which calls WPF `DesignerProperties`) only runs for real in a WPF or hosted-designer context — the view model itself is not instantiable outside that container.

### Relationships

- **`Mvvm.ViewModelBase`** (`Mvvm/ViewModelBase.cs`) — the shared base class for view models; here it contributes `ObservableObject` inheritance plus design-mode detection and child-view-model bookkeeping. Nothing in this class overrides or uses the child-view-model API.
- **`IShowUsersViewModel`** (`UserManagement/ViewModel/IShowUsersViewModel.cs`) — the contract this class implements: `Users`, the two imported services, the generated `LoadedCommand`, and `OnLoadedAsync`.
- **`IUserService`** (`BusinessLayer/IUserService.cs`) — imported via MEF; this class calls `GetActiveUsers()`, which returns `Task<List<UserDto>>`. `UserDto` lives in the `Dto` namespace; it is not a `UserModel` and is not referenced anywhere else in this class's dependencies (the `Entity.Hibernate` using statement in the file is unused by any code shown).
- **`ILoggingService`** (`Logging`) — imported but never read or written by this class.
- **`UserChangedMessage` / `UserChangeType`** (`UserManagement/Messaging/`) — the message type this class subscribes to. `UserChangedMessage` carries a `UserModel` in `Value` plus a `UserChangeType`. The only sender in the codebase is `AddUserViewModel`, which broadcasts `UserChangeType.Added` after a successful save.
- **`UserModel`** (`UserManagement/Model/UserModel.cs`) — an `ObservableObject` with `FirstName`/`LastName` used as the display model in `Users`.
- **`UserViewModel`** — the direct consumer; it exposes this view model to its view via the `ShowUsersViewModel` property.

### Behavior & Details

**Construction.** The constructor registers `this` as a recipient of `UserChangedMessage` on `WeakReferenceMessenger.Default`. Because the registration is weakly referenced, messages are delivered only while the container keeps an instance alive. On each message it switches on `message.UserChangeType`:

- `Added` — appends `message.Value` to `Users`.
- `Updated` / `Deleted` — throws `NotImplementedException`. So if such a message were ever sent, the handler faults rather than the list going stale; as of now, `AddUserViewModel` is the only sender and only ever sends `Added`, so these branches are unreachable in practice.

**Initial load.** `OnLoadedAsync` (exposed to the view as `LoadedCommand` through the source generator) awaits `UserService.GetActiveUsers()`, maps each `UserDto` to a fresh `UserModel` copying only `FirstName` and `LastName`, and appends them to `Users`. There is no guard against a second invocation: triggering `LoadedCommand` twice duplicates every user in the collection.

**Data flow.** There are two ways a user reaches `Users`: the initial bulk load from the service, and appends driven by `Added` messages. Note the two paths construct their `UserModel`s differently — the load maps a `UserDto` explicitly, while the message path uses the `UserModel` the sender already built (in `AddUserViewModel`'s case, constructed from its form fields).

**State.** `Users` is an `ObservableCollection<UserModel>` with a read-only accessor, so the view can bind to it and see additions; external code can only add through this view model's own paths. The `UserService` and `LoggingService` properties are writable by the MEF container only; the class sets no other state.

### Rough edges

- `Updated` and `Deleted` handlers throw `NotImplementedException`, so the collection cannot reflect edits or removals, and the throw means a future sender of those messages crashes the handler rather than degrading gracefully.
- `LoggingService` is imported but unused.
- The `using Entity.Hibernate;` directive references a project none of the visible code uses.
- `OnLoadedAsync` appends to `Users` without clearing or deduplicating, so re-invoking the load command duplicates the list.

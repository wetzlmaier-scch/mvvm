# WpfApp1/View/UserView.xaml

### Purpose

This file is the WPF XAML for `UserView`, the main window of the `WpfApp1` host application — the "User Management" screen where a user sees the current list of users and can add a new one. The matching code-behind (`WpfApp1/View/UserView.xaml.cs`) is thin: it just calls `InitializeComponent()` and exports the window as `IMainView<bool?, double>`. All behaviour lives in the view-models bound here, so this file is pure layout, bindings, and styling.

### Role in the Codebase

`UserView` is the entry-point window of `WpfApp1`. It is not constructed directly by application code: `WpfApp1/Controller/DefaultModuleController.cs` imports `IMainView<bool?, double>` via MEF, which resolves to `UserView` (exported in its code-behind). The controller assigns `MainView.DataContext = mainViewModel`, where `mainViewModel` is the MEF-resolved `UserViewModel` (`UserManagement/ViewModel/UserViewModel.cs`), then shows the window via `MainView.Show()`.

All bindings in this XAML therefore target properties on `UserViewModel` and its two MEF-imported child view-models, `ShowUsersViewModel` and `AddUserViewModel`. The XAML itself contains no code logic beyond the `Loaded` event trigger described below. A sibling host, `WinFormsApp1/View/UserForm.cs`, binds to the same view-models for the WinForms version of the same feature.

### Relationships

- **`UserViewModel`** (`UserManagement/ViewModel/UserViewModel.cs`) — the root data context. It is `MainViewModelBase`, carries `[Export(typeof(IUserViewModel))]` and `[Export(typeof(IMainViewModel))]`, and exposes the two child view-models as `[Import]` properties: `IAddUserViewModel AddUserViewModel` and `IShowUsersViewModel ShowUsersViewModel`.
- **`ShowUsersViewModel`** (`UserManagement/ViewModel/ShowUsersViewModel.cs`) — binds the `Users` collection into the left list; its `LoadedCommand` (generated from `OnLoadedAsync`) is fired on window load; it listens to `UserChangedMessage` and appends new users to `Users` itself.
- **`AddUserViewModel`** (`UserManagement/ViewModel/AddUserViewModel.cs`) — binds `FirstName`, `LastName`, and `SaveUserCommand`. `SaveUserCommand` is generated by the CommunityToolkit `[RelayCommand]` from `SaveUserAsync`, so `IsRunning` is available to the button's `DataTrigger`.
- **`DesignUserViewModel`** (`UserManagement/Design/DesignUserViewModel.cs`) — design-time-only data context (`d:DesignInstance`), so the layout renders in the Visual Studio designer without a real MEF composition.
- **`DebugConverter`** (`Common/Converter/DebugConverter.cs`) — declared as the resource `MyDebugConverter`, but its only usage is the commented-out `TextBox` binding. The resource is effectively dead code.

### Behavior & Details

**Layout.** A 700×450 window with a 2-column `Grid`: the left column (wider) is a white rounded `Border` titled "Current Users" containing a `ListView` with `First Name` and `Last Name` columns; the right column is a white `Border` titled "Add New User" with two `TextBox`es and a Save button. A window-level `Style TargetType="TextBox"` sets padding and borders for both inputs.

**Loading the user list.** The `b:EventTrigger` on `Loaded` invokes `ShowUsersViewModel.LoadedCommand`, which asynchronously calls `UserService.GetActiveUsers()` and populates the `Users` collection. Note the trigger is bound to the child view-model command, not to anything on the root `UserViewModel`.

**Adding a user and validation.** Both text boxes bind with `UpdateSourceTrigger=PropertyChanged` and `ValidatesOnNotifyDataErrors=True`. `AddUserViewModel` implements `INotifyDataErrorInfo` (via `ValidatableViewModelBase<IUser>`) and calls `ValidateProperty` on each change, so validation errors appear as the user types.

- The **First Name** box uses a custom `InlineErrorTemplate` (a `ControlTemplate` defined in the right panel's resources) that renders the first validation error in red beneath the field.
- The **Last Name** box has no error template; instead it shows the first error as a red tooltip via `ToolTip="{Binding (Validation.Errors)[0].ErrorContent, RelativeSource={RelativeSource Self}}"`. The two fields thus display the same kind of error in two different ways.

**Save button.** Binds to `AddUserViewModel.SaveUserCommand`. A `DataTrigger` on `SaveUserCommand.IsRunning` swaps the content from "Save User" to "Saving..." while the async command runs; a disabled button renders at 60% opacity. When `SaveUserAsync` succeeds, the view-model sends a `UserChangedMessage` and clears its own fields, which the bound text boxes reflect automatically.

**Window icon.** `Icon="{Binding Icon}"` binds to an `Icon` property inherited from the `ViewModelBase`/`MainViewModelBase` chain in `Mvvm`; `MainViewModelBase` is defined there but the `Icon` member is not verified in the files loaded here.

### Rough edges

- The `MyDebugConverter` resource is declared but only referenced by a commented-out `TextBox` binding — it is dead markup, and `DebugConverter.Convert` calls `Debugger.Break()`, so uncommenting it would drop a breakpoint on every binding update.
- The two input fields use inconsistent error presentation (inline template vs. tooltip), so the same validation failure looks different depending on which field is wrong.
- The commented-out binding also suggests the `DesignUserViewModel`/design instance usage predates a renamed property, but the code-behind and exports are what actually wire the window at runtime.
